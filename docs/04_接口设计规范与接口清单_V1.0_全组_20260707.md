# 生物医药数字信息系统接口设计规范与接口清单

> 版本：V1.0｜RESTful 风格｜适用范围：后端开发、前后端联调、测试与文档审查

| 项目 | 内容 |
| --- | --- |
| 项目名称 | 生物医药数字信息系统 |
| 接口风格 | RESTful API |
| 数据格式 | JSON；文件上传使用 multipart/form-data |
| 认证方式 | Authorization: Bearer <token> |
| 接口前缀 | /api |
| 说明 | 本文档给出接口设计规范和资源化接口清单，避免动作式 URL、方法滥用、状态码混乱和响应格式不统一。 |

## 1. 接口设计总体原则

- 接口路径以资源为中心，使用名词表达资源，不在路径中使用 get、add、update、delete、query、list、save、do、handle 等动作词。

- 资源集合统一使用复数形式，例如 users、roles、herbs、courses、files。

- 使用 HTTP 方法表达操作语义：GET 查询，POST 创建资源或提交复杂业务记录，PUT 整体更新，PATCH 局部更新，DELETE 删除。

- 分页、排序、关键词、状态、时间范围和筛选条件统一放在 Query 参数中。

- 新增、更新和局部修改接口使用 JSON 请求体；文件上传使用 multipart/form-data。

- 路径层级原则上不超过三层，复杂查询通过 Query 参数表达，避免路径过深。

- 业务状态流转尽量资源化表达，如提交记录、审核记录、归档记录、确认记录和重试记录。

- 除登录接口外，所有受保护接口均要求携带 Bearer Token，并进行角色权限和数据范围校验。

## 2. 通用请求规范

### 2.1 Header 规范

| Header 名称 | 是否必填 | 说明 |
| --- | --- | --- |
| Authorization | 受保护接口必填 | 格式为 Bearer <token>，用于身份认证。 |
| Content-Type | 写操作必填 | 普通 JSON 请求使用 application/json；文件上传使用 multipart/form-data。 |
| Accept | 建议填写 | 建议为 application/json。 |

### 2.2 Query 参数规范

| 参数 | 说明 | 示例 |
| --- | --- | --- |
| page | 页码，从 1 开始。 | page=1 |
| size | 每页条数。 | size=10 |
| keyword | 关键词搜索。 | keyword=黄连 |
| sort | 排序字段和方向。 | sort=createTime,desc |
| status | 状态筛选。 | status=SUBMITTED |
| startTime / endTime | 时间范围筛选。 | startTime=2026-07-01&endTime=2026-07-12 |

### 2.3 请求体命名规范

- JSON 字段统一使用小驼峰命名，例如 herbId、baseId、collectTime、businessType。

- ID 字段命名统一为 xxxId，例如 userId、roleId、fileId。

- 状态字段使用明确枚举值，例如 DRAFT、SUBMITTED、APPROVED、REJECTED、ARCHIVED。

- 不得将复杂对象、数组、长文本、密码、Token 等内容放入 URL。

## 3. 状态码与响应格式

### 3.1 HTTP 状态码

| 状态码 | 使用场景 |
| --- | --- |
| 200 OK | 查询成功或普通操作成功。 |
| 201 Created | 资源创建成功。 |
| 204 No Content | 删除成功且无返回体。 |
| 400 Bad Request | 请求参数错误、字段校验失败或请求体格式错误。 |
| 401 Unauthorized | 未登录、Token 缺失或 Token 失效。 |
| 403 Forbidden | 已登录但无权限访问该资源或执行该操作。 |
| 404 Not Found | 请求资源不存在。 |
| 409 Conflict | 资源冲突，例如重复账号、重复标准版本、状态冲突。 |
| 500 Internal Server Error | 服务器内部错误。 |

### 3.2 统一响应格式

普通成功响应建议统一返回以下结构。HTTP status 表达传输和协议层结果，业务 code 表达业务层结果，二者不得混用。

```json
{
  "code": "SUCCESS",
  "message": "操作成功",
  "data": {},
  "timestamp": "2026-07-07T10:00:00+08:00"
}
```

### 3.3 分页响应格式

```json
{
  "code": "SUCCESS",
  "message": "查询成功",
  "data": {
    "records": [],
    "page": 1,
    "size": 10,
    "total": 0
  },
  "timestamp": "2026-07-07T10:00:00+08:00"
}
```

### 3.4 错误响应格式

```json
{
  "code": "VALIDATION_ERROR",
  "message": "请求参数错误",
  "data": {
    "field": "name",
    "reason": "名称不能为空"
  },
  "timestamp": "2026-07-07T10:00:00+08:00"
}
```

## 4. 幂等性与安全要求

| 项目 | 设计要求 |
| --- | --- |
| 幂等性 | GET、PUT、DELETE 应具有幂等性；POST 通常不要求幂等；PATCH 按具体字段修改语义设计。 |
| 认证 | 除登录接口外，所有接口均通过 Authorization Header 携带 Bearer Token。 |
| 权限 | 用户、角色、文件、审核、申报、业绩、SOAP 交换等敏感接口必须进行权限控制。 |
| 敏感数据 | URL 中不得暴露密码、Token、身份证号等敏感信息。 |
| 日志 | 新增、修改、删除、审核、下载、归档、SOAP 交换等关键操作应写入操作日志。 |
| 删除策略 | 重要业务数据建议逻辑删除；删除接口成功且无返回体时使用 204 状态码。 |

## 6. 后续开发约束

- 前端不得直接访问数据库，所有业务数据必须通过后端接口获取。

- 后端 Controller 不直接操作数据库，业务逻辑由 Service 负责，数据库访问由 Mapper 负责。

- 新增接口必须先检查路径是否资源化、方法是否符合语义、参数是否放置合理、响应格式是否统一。

- 新增业务状态流转接口时，应优先建模为记录类子资源，例如 audit-records、submissions、archives。

- 接口文档、前端请求封装和后端实现应保持一致，避免同一资源出现多套命名。
