# 生物医药数字信息系统版本控制规则说明

> 版本：V1.0  
> 分支模型：main + dev + feature  
> 适用范围：项目代码、配置文件、接口文档、数据库脚本、前后端联调与阶段提交管理

## 1. 编写目的

为保证生物医药数字信息系统在多人协作开发过程中的代码版本清晰、修改过程可追踪、阶段成果可回退，项目采用基于 Git 的版本控制管理方式。

本规则用于约定项目分支模型、分支职责、提交规范、合并流程、冲突处理、版本发布和团队协作要求，避免出现直接覆盖代码、分支混乱、提交信息不清晰、无法定位问题来源等情况。

## 2. 分支模型

本项目采用 `main + dev + feature` 三类分支模型。

```text
main
└── dev
    ├── feature/user-auth
    ├── feature/herb-resource
    ├── feature/growth-collection
    ├── feature/course-research
    └── feature/performance-review
```

三类分支含义如下：

| 分支 | 定位 | 说明 |
| --- | --- | --- |
| main | 主分支 / 稳定分支 | 保存可提交、可演示、可部署的稳定版本，不直接开发。 |
| dev | 开发集成分支 | 保存阶段开发成果，所有 feature 分支完成后先合并到 dev。 |
| feature | 功能开发分支 | 每个具体功能、模块、修复任务从 dev 拉出，开发完成后合并回 dev。 |

## 3. 分支职责

### 3.1 main 分支

`main` 分支用于保存项目稳定版本。

规则如下：

1. `main` 分支只接收来自 `dev` 分支的阶段性合并。
2. `main` 分支不允许直接提交业务代码。
3. `main` 分支中的代码应保证能够正常运行、演示和提交。
4. 每次合并到 `main` 前，应完成基本测试、冲突检查和文档同步。
5. 每次重要提交后，可打版本标签，例如 `v1.0.0`。

### 3.2 dev 分支

`dev` 分支用于日常开发集成。

规则如下：

1. 所有功能分支必须从最新 `dev` 分支拉出。
2. 功能开发完成后，先合并回 `dev` 分支。
3. `dev` 分支应尽量保持可运行状态，不能长期保留无法启动或严重报错的代码。
4. 多人协作时，合并前应先拉取最新 `dev`，解决冲突后再提交。
5. 阶段开发完成并通过测试后，再由 `dev` 合并到 `main`。

### 3.3 feature 分支

`feature` 分支用于具体功能开发或问题修复。

规则如下：

1. 每个功能、模块或修复任务单独创建一个 `feature` 分支。
2. `feature` 分支从 `dev` 创建，不从 `main` 直接创建普通开发分支。
3. 一个 `feature` 分支只完成一个明确任务，避免多个无关功能混在同一分支中。
4. 功能完成、自测通过后，合并回 `dev`。
5. 合并完成后，已无继续使用价值的 `feature` 分支可以删除。

## 4. 分支命名规范

### 4.1 基本格式

```text
feature/模块名-功能说明
```

命名要求：

1. 使用英文小写字母、数字和短横线。
2. 不使用中文、空格和特殊符号。
3. 名称应能看出开发内容。
4. 同一模块下的不同任务应使用不同分支名。

### 4.2 推荐示例

```text
feature/user-auth
feature/role-permission
feature/herb-resource
feature/growth-collection
feature/soap-exchange
feature/course-management
feature/training-process
feature/evaluation-application
feature/performance-review
feature/file-archive
```

### 4.3 不推荐示例

```text
feature/test
feature/new
feature/my-code
feature/final
feature/zhangsan
feature/修改一下
```

## 5. 提交信息规范

### 5.1 提交格式

提交信息建议采用以下格式：

```text
类型: 简要说明
```

常用类型如下：

| 类型 | 含义 | 示例 |
| --- | --- | --- |
| feat | 新增功能 | feat: 新增中药材档案管理 |
| fix | 修复问题 | fix: 修复用户登录状态失效问题 |
| docs | 文档修改 | docs: 更新接口设计说明 |
| style | 格式调整 | style: 调整前端页面样式 |
| refactor | 重构代码 | refactor: 优化权限校验逻辑 |
| test | 测试相关 | test: 增加业绩审核测试用例 |
| chore | 构建、配置、杂项 | chore: 更新项目启动配置 |

### 5.2 提交要求

1. 一次提交只描述一个相对完整的修改点。
2. 提交信息应说明“做了什么”，避免只写 `update`、`fix bug`、`修改`。
3. 不提交无关文件、临时文件、缓存文件和本地 IDE 配置。
4. 提交前应确认项目能正常编译或启动。
5. 文档、数据库脚本和代码变更应尽量同步提交，避免版本不一致。

## 6. 开发流程

### 6.1 新功能开发流程

1. 切换到 `dev` 分支。
2. 拉取最新代码。
3. 从 `dev` 创建新的 `feature` 分支。
4. 在 `feature` 分支完成开发。
5. 本地自测功能是否正常。
6. 提交代码并推送远程分支。
7. 将 `feature` 合并到 `dev`。
8. 在 `dev` 分支进行集成测试。
9. 阶段稳定后，将 `dev` 合并到 `main`。

示例命令：

```bash
git checkout dev
git pull
git checkout -b feature/herb-resource

# 开发完成后
git add .
git commit -m "feat: 新增中药材档案管理"
git push -u origin feature/herb-resource
```

### 6.2 合并到 dev

合并前应先更新本地 `dev`：

```bash
git checkout dev
git pull
git merge feature/herb-resource
```

如出现冲突，应先解决冲突，再提交合并结果。

### 6.3 合并到 main

当 `dev` 分支达到阶段稳定状态后，才允许合并到 `main`：

```bash
git checkout main
git pull
git merge dev
git tag v1.0.0
git push
git push origin v1.0.0
```

## 7. 合并规则

1. `feature` 只能合并到 `dev`。
2. `dev` 只能在阶段稳定时合并到 `main`。
3. `main` 不接收未测试的功能分支。
4. 合并前应确认没有未提交代码。
5. 合并后应检查项目是否能正常启动。
6. 发生冲突时，由熟悉相关模块的成员负责处理。
7. 合并完成后，应删除已经完成的临时 `feature` 分支。

## 8. 冲突处理规则

代码冲突处理要求如下：

1. 先确认冲突文件属于哪个模块。
2. 不确定业务含义时，不得随意删除他人代码。
3. 冲突处理后必须重新运行或检查相关功能。
4. 文档冲突应保留最新有效内容，并删除重复段落。
5. 数据库脚本冲突应重点检查表结构、字段、索引和初始化数据是否重复。
6. 冲突解决完成后，提交信息中应说明已处理冲突。

示例：

```text
fix: 处理用户权限模块合并冲突
```

## 9. 版本标签规则

`main` 分支形成稳定版本后，可以打标签。

推荐格式：

```text
v主版本.次版本.修订版本
```

示例：

| 标签 | 含义 |
| --- | --- |
| v0.1.0 | 初始可运行版本 |
| v0.5.0 | 基本功能完成版本 |
| v1.0.0 | 正式提交版本 |
| v1.1.0 | 小范围功能补充版本 |
| v2.0.0 | 结构或功能大改版本 |

## 10. 文件与文档版本控制要求

1. 正式文档应按项目文档命名规范命名。
2. 文档修改应提交到 Git，避免只在本地保存。
3. 大型二进制文件、临时截图、运行日志不建议频繁提交。
4. 数据库脚本应与代码版本同步维护。
5. 接口设计、模块设计、数据库设计发生调整时，应同步更新对应文档。
6. 不提交账号密码、Token、数据库连接密钥等敏感信息。

## 11. 团队协作要求

1. 每位成员开发前先拉取最新 `dev`。
2. 每位成员只在自己的 `feature` 分支上开发。
3. 重要功能合并前，应通知相关成员检查影响范围。
4. 公共模块、权限模块、数据库结构变更应提前沟通。
5. 不允许在不了解代码含义的情况下大范围格式化或重构他人模块。
6. 每天结束前应提交当天稳定修改，避免代码只保存在个人电脑中。
7. 阶段提交前由全组统一检查 `dev` 和 `main` 状态。

## 12. 推荐执行策略

考虑本项目属于短周期小组实训项目，建议采用轻量但清晰的执行策略：

1. `main` 保存最终可提交成果。
2. `dev` 保存每天集成后的最新成果。
3. 每个成员按模块创建自己的 `feature` 分支。
4. 每天至少进行一次 `feature` 到 `dev` 的集成。
5. 重大功能完成后再从 `dev` 合并到 `main`。
6. 答辩前冻结 `main`，只允许修复明确问题，不再随意增加新功能。

## 13. 规则摘要

本项目采用 `main + dev + feature` 的版本控制模型。`main` 用于保存稳定提交版本，`dev` 用于日常开发集成，`feature` 用于具体功能开发。所有开发任务从 `dev` 拉出 `feature` 分支，完成后合并回 `dev`，阶段稳定后再由 `dev` 合并到 `main`。通过统一分支模型、提交信息、合并流程和版本标签，可以保证项目开发过程清晰可追踪，降低多人协作中的代码覆盖、冲突混乱和版本不可回退风险。
