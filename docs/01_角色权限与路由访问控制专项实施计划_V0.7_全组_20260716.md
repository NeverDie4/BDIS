## 1. 调整说明

冻结说明：本文保留已完成的 P0 记录和后续设计，剩余任务统一延期。当前系统行为以代码、OpenAPI、权限迁移和冻结版文档索引为准。

本版本根据小组当前分工收缩实施范围。以下业务已有其他成员开发，本计划不再安排对应页面和业务实现：

- 主界面和登录界面。
- 药材资源及相关业务页面。
- 实验教学和课程模块。
- 课题、实验记录、培训、评价、申报、业绩等教学科研及管理业务。
- 移动端和移动采集页面。

本计划只解决各模块共同依赖的角色、权限、菜单、路由守卫、数据范围和后台授权问题。对于其他成员负责的页面，我们提供公共能力和接入规范，不主动调整其页面结构、样式、业务表单或接口封装。

## 2. 编写目的

当前系统已经具备登录、JWT、RBAC、菜单权限、按钮权限和部分数据范围能力，但还存在以下公共问题：

1. 门户页面缺少统一的页面级访问控制。
2. 未加载当前用户时可能短暂显示无权限菜单。
3. 后台子路由只校验登录状态，没有统一校验页面权限。
4. 页面、菜单、按钮和接口权限缺少一致性约束。
5. 当前只有 5 个预置角色，需求中的业务身份尚未形成可落地的角色模板。
6. 普通业务成员正在并行开发页面，如果每个模块自行实现鉴权，容易出现重复逻辑和行为差异。

本计划的目标是建立一套可以被所有业务模块复用的访问控制基础，并在尽量少修改他人页面的前提下完成集成。

## 3. 实施原则

1. **公共能力优先**：只实现各业务模块都需要的角色和鉴权基础。
2. **少改业务页面**：通过全局 Provider、布局和公共组件接入权限，不重构他人页面。
3. **权限码优先**：页面和接口判断权限码，不直接写死角色编码。
4. **后端最终裁决**：前端隐藏和路由守卫只改善体验，后端权限及数据范围才是安全边界。
5. **兼容现有数据**：保留现有 5 个角色编码，不修改已经执行的 Flyway 历史迁移。
6. **模块自行声明**：业务负责人提供本模块路由和权限清单，权限负责人负责公共校验和聚合。
7. **避免中心文件冲突**：路由和权限元数据按模块拆分，不要求所有成员同时修改一个大配置文件。
8. **执行文档可归档**：计划完成后不继续充当系统说明，长期规则迁移至设计和测试文档。

2. 让导航读取统一的可见路由结果，不调整导航视觉。
3. 在业务页面入口增加一层权限声明，不修改页面主体。

## 5. 当前基线

### 5.1 当前预置角色

| 角色编码    | 名称       | 默认数据范围 | 当前定位             |
| ----------- | ---------- | ------------ | -------------------- |
| `ADMIN`     | 系统管理员 | all          | 系统管理和全部权限   |
| `TEACHER`   | 教师       | department   | 教师及部门业务       |
| `STUDENT`   | 学生       | self         | 本人和只读业务       |
| `COLLECTOR` | 采集人员   | self         | 数据采集和上传       |
| `REVIEWER`  | 审核人员   | department   | 审核、复核和部分日志 |

现有角色均保留。是否收窄 `REVIEWER`、是否新增更细的审核角色，需要和对应业务负责人一起确认，不能由权限基础设施单方面决定。

### 5.2 当前公共访问控制问题

1. 当前 Token 保存在浏览器本地存储中，Next.js Middleware 无法直接读取。
2. 门户主要依赖业务 API 返回 401 后跳转登录，不是统一的页面进入判断。
3. `HeaderNav` 在 `user` 尚未加载时可能显示全部入口。
4. `DashboardShell` 只验证 Token 和当前用户，未对当前子路由校验页面权限。
5. 后台菜单来源于 `/me/menus`，但前端没有检查菜单 routePath 是否真实存在。
6. 业务页面各自调用 `hasPermission`，缺少统一页面守卫和统一空状态。
7. 401、403、Token 失效和无数据有时由页面自行处理，行为不一致。

## 6. 目标角色与权限模型

### 6.1 角色建模规则

1. `user_type` 表示账号主体类型，角色表示授权集合，两者不混用。
2. 同一用户允许绑定多个角色，功能权限取并集。
3. 数据范围按现有规则合并，不能简单用字符串大小比较。
4. 系统预置角色不可删除，可以停用业务角色，但 `ADMIN` 必须保留至少一个有效用户。
5. 页面只声明主权限，例如 `auth:user:view`；具体按钮继续使用 create/update/delete 等权限。
6. 自定义角色只要获得相同权限，应与预置角色产生相同页面行为。

### 6.2 建议角色目录

我们负责维护角色目录和编码规则，但新增业务角色必须由对应模块负责人确认权限清单后再迁移。

## 7. 路由访问控制方案

### 7.1 三层控制

```text
路由层：是否登录、是否拥有页面主权限
组件层：按钮、Tab、字段、下载和批量操作权限
后端层：接口权限、数据范围和资源归属
```

路由层和组件层负责防止无权限入口暴露，后端层负责防止真实越权。

### 7.2 模块化路由清单

不建立所有人都要修改的单一大文件，建议采用：

```text
frontend/src/config/routes/
├── index.ts
├── public.ts
├── auth-admin.ts
├── herb.ts          # 药材负责人维护
├── teaching.ts      # 课程负责人维护
├── research.ts      # 相关业务负责人维护
└── mobile.ts        # 移动端负责人维护；本计划不修改页面
```

每个模块导出统一结构：

```ts
type RouteMeta = {
  path: string;
  title: string;
  permission?: string;
  public?: boolean;
  menu?: boolean;
  owner: string;
};
```

我们的代码只维护 `index.ts` 聚合逻辑、公共类型和 `auth-admin.ts`。业务模块负责人维护自己的路由项，减少合并冲突。

### 7.3 会话初始化状态

统一会话状态：

```text
unknown -> authenticated
unknown -> anonymous
authenticated -> expired
```

行为要求：

1. `unknown` 时显示统一加载状态，不渲染业务页面和权限菜单。
2. 无 Token 或 `/auth/me` 返回 401，进入登录页。
3. 已登录但缺少页面权限，进入 `/forbidden`，不得注销有效会话。
4. 权限通过后再挂载页面组件，避免业务请求先发出。
5. 登录回跳只接受站内路径，拒绝外部 URL。

### 7.4 公共组件

计划新增：

| 组件/Hook            | 职责                                   |
| -------------------- | -------------------------------------- |
| `AuthBoundary`       | 等待会话初始化并区分匿名和已登录状态   |
| `PermissionBoundary` | 校验当前路由主权限                     |
| `PermissionGate`     | 控制按钮、Tab 和局部功能显示           |
| `usePermission`      | 提供单权限判断                         |
| `useAnyPermission`   | 判断任一权限                           |
| `useAllPermissions`  | 判断全部权限                           |
| `resolveRouteAccess` | 根据 pathname 和路由元数据计算访问结果 |

其他成员可以逐步接入这些组件，不要求本计划一次性改完所有业务页面。

### 7.5 401、403 和回跳

| 状态 | 含义                         | 统一行为                             |
| ---- | ---------------------------- | ------------------------------------ |
| 401  | 未登录、Token 过期、会话撤销 | 清理会话并跳转登录，保留安全回跳地址 |
| 403  | 已登录但无权限               | 保留会话并显示 `/forbidden`          |
| 404  | 路由或资源不存在             | 显示不存在，不跳登录                 |
| 409  | 业务状态冲突                 | 页面提示刷新，不改变登录状态         |

业务页面不再自行实现登录跳转。登录页视觉和表单仍由原负责人维护，我们只约定其登录成功后读取安全 `returnUrl`。

### 7.6 Token 方案

本轮采用最小变更：

- 保留现有 Bearer Token 和 Axios 请求拦截器。
- 使用客户端访问控制组件，因为浏览器本地存储无法被 Next.js Middleware 可靠读取。
- 不在本轮修改登录协议、登录 UI 或引入 BFF。

HttpOnly Cookie/BFF 作为独立安全改造议题。如果后续实施，必须同时设计 CSRF、同源代理、注销、刷新和开发环境跨域，不能混入本轮权限页面优化。

## 9. 实施阶段

### 阶段 0：冻结边界与接口

任务：

1. 确认本计划列出的目录归属。
2. 确认各业务模块的路由清单负责人。
3. 确认候选新增角色及对应业务负责人。
4. 建立业务权限清单模板。

验收：不存在我们和其他成员同时修改同一业务页面的安排。

### 阶段 1：公共路由守卫 P0

任务：

1. 建立模块化路由元数据类型和聚合器。
2. 实现统一会话初始化状态。
3. 实现 `AuthBoundary` 和 `PermissionBoundary`。
4. 新增 `/forbidden`。
5. 统一 401、403 和安全回跳。
6. 给业务负责人提供路由清单接入示例。

验收：匿名用户不能进入受保护路由；已登录无权限用户不会被注销；权限判断期间不挂载业务页面。

### 阶段 2：角色、权限与数据范围 P0

任务：

1. 保留现有 5 个角色并建立系统角色保护规则。
2. 收集其他模块提交的角色和权限清单。
3. 只为已确认权限的业务角色编写增量迁移。
4. 校验多角色权限并集和角色停用行为。
5. 校验数据范围在列表、详情和写操作中的一致性。
6. 增加角色权限矩阵自动化测试。

验收：不出现空角色；角色权限来自确认后的业务清单；自定义角色与预置角色按相同权限码运行。

### 阶段 3：权限后台增强 P0/P1

任务：

1. 为 `/dashboard/**` 增加页面级权限守卫。
2. 完善用户分配角色、角色分配权限和数据范围展示。
3. 保护系统角色，阻止删除关键角色。
4. 增加菜单 routePath 与前端路由清单的一致性提示。
5. 统一后台按钮的 `PermissionGate`。
6. 在无其他负责人的情况下再实现审计或字典后台页。

验收：直接输入后台子路由时正确得到允许或禁止结果；无权限按钮不显示，接口也返回 403。

### 阶段 4：业务模块集成验收

本阶段不代替业务负责人改页面，只执行以下检查：

1. 每个业务路由已声明主权限。
2. 服务端菜单和前端 routePath 一致。
3. 页面按钮使用公共权限组件或等价实现。
4. 后端接口有对应权限校验。
5. 业务负责人提供至少一个允许角色和一个拒绝角色测试。
6. 发现问题后提交明确的文件、权限码和预期行为，由页面负责人修改。

主界面、登录、药材、教学科研和移动端只参加本阶段验收，不进入我们的开发任务。

4. 将本计划状态改为已完成或部分完成。

验收：代码、正式设计文档和测试报告能够说明当前系统，本计划不再承担现状说明职责。

## 14. 文档生命周期与过时处理

### 14.1 为什么本计划会过时

本文件描述的是“准备做什么、按什么顺序做”，不是“系统现在是什么”。当任务完成、负责人变化或实现方案调整后，排期、阶段和未完成事项会自然失效。因此它大概率会在实施完成后过时，这是执行计划的正常生命周期。

### 14.2 执行期间如何维护

文档状态使用以下四种之一：

```text
评审中 -> 执行中 -> 已完成
                 -> 已被替代
```

只在以下节点更新计划：

- 范围或负责人发生变化。
- 阶段完成或被取消。
- 技术路线发生重要调整。
- 出现需要其他成员确认的阻塞项。

不把每天的实现细节持续堆入计划，具体结果进入 Git 提交、测试报告和正式设计文档。

### 14.3 完成后如何处理

计划完成时：

1. 将最终角色与权限矩阵同步到需求或权限设计文档。
2. 将路由守卫、401/403 和数据范围方案同步到模块设计说明书。
3. 将实际接口权限同步到接口清单。
4. 将角色和越权验证结果同步到测试文档。
5. 在本文件头部标记完成日期、完成范围和未完成事项。
6. 确认长期文档已经接管后，将本计划移入 `docs/deprecated/`，不删除历史。

因此，完成后继续阅读本计划只能用于追溯当时的决策过程，不能用它判断当前系统功能。当前系统状态应以代码、OpenAPI、数据库迁移和最新设计/测试文档为准。
