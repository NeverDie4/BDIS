# BDIS Flyway 数据库迁移规则

> 版本：V1.0  
> 日期：2026-07-08  
> 适用数据库：MySQL 8.0.x  
> 适用范围：数据库初始化、表结构变更、索引约束调整、必要字典数据维护  
> 相关文档：[05_数据库详细设计说明书_V1.0_全组_20260710.md](05_数据库详细设计说明书_V1.0_全组_20260710.md)、[05_数据库命名规范设计方案_V1.0_全组_20260707.md](05_数据库命名规范设计方案_V1.0_全组_20260707.md)

## 1. 文档目的

本文档用于约束 BDIS 项目 Flyway 数据库迁移脚本的编写、提交、执行和问题处理流程，保证团队成员在同一套数据库版本规则下协作。

项目数据库以 MySQL 8.0.x 为准。个人本地如使用其他兼容数据库，只作为个人开发环境选择，不作为迁移脚本编写、评审和验收依据。

## 2. 基本原则

1. Flyway migration 是数据库结构变更的唯一正式来源。
2. 数据库设计已经确认后，初始化建表和后续结构变化都应通过 migration 管理。
3. 已合并并执行过的版本迁移脚本不得修改、重命名或删除。
4. 后续结构调整必须新增 migration，不得直接改历史 migration。
5. 常规迁移使用独立 `flyway` 模块执行，Spring Boot 默认不自动执行 Flyway，避免后端启动时误改共享数据库。
6. 迁移脚本不得写入数据库账号、密码、个人路径或本地端口。
7. 迁移脚本必须能在空的 MySQL 8.0.x 数据库中按版本顺序完整执行。

## 3. 数据库与字符集约定

| 项目         | 规则               |
| ------------ | ------------------ |
| 数据库类型   | MySQL 8.0.x        |
| 存储引擎     | InnoDB             |
| 字符集       | utf8mb4            |
| 排序规则     | utf8mb4_0900_ai_ci |
| 时区         | Asia/Shanghai      |
| 表名字段名   | 小写英文 + 下划线  |
| SQL 文件编码 | UTF-8              |
| SQL 文件换行 | LF                 |

迁移脚本只负责在已存在的项目数据库中创建和变更对象，不负责创建 MySQL 用户、授权账号或创建多个环境数据库。

## 4. 脚本目录

当前独立 `flyway` 模块位于：

```text
flyway/pom.xml
```

正式 migration 文件路径为：

```text
backend/src/main/resources/db/migration
```

项目只有这一套正式 migration 文件来源，不能在后端模块和独立模块中复制两份脚本。独立 `flyway` 模块通过 Maven Flyway 插件引用该目录执行迁移。

## 5. 文件命名规则

版本迁移脚本使用 Flyway 标准命名：

```text
V版本号__英文描述.sql
```

推荐格式：

```text
V20260708_001__init_schema.sql
V20260708_002__init_dictionary_data.sql
V20260709_001__add_herb_growth_indexes.sql
```

命名要求：

1. `V` 必须大写。
2. 版本号使用日期加序号，格式为 `YYYYMMDD_序号`。
3. 版本号和描述之间必须使用两个下划线 `__`。
4. 描述使用小写英文和下划线，不使用中文、空格和特殊符号。
5. 同一天多份脚本按 `_001`、`_002`、`_003` 递增。
6. 不使用 `final`、`new`、`test`、`latest` 等模糊描述。
7. 初始版本脚本命名为 `V20260708_001__init_schema.sql`。

## 6. 初始化脚本边界

第一版初始化脚本只包含数据库结构定义：

1. 表结构。
2. 主键、唯一约束、必要外键。
3. 普通索引。
4. 字段默认值。
5. 表注释和字段注释。
6. 必要的 `created_at`、`updated_at`、`is_deleted`、`version` 等通用字段。

第一版初始化脚本不包含：

1. 测试数据。
2. 演示数据。
3. 个人账号。
4. 开发环境专用数据。
5. 数据库创建、用户创建、授权语句。
6. 和已确认数据库设计无关的临时表或实验表。

## 7. 字典数据规则

必要字典数据可以单独放入版本脚本，例如：

```text
V20260708_002__init_dictionary_data.sql
```

字典数据规则：

1. 只写系统运行必须存在的基础字典。
2. 不写用于演示的样例业务数据。
3. 字典编码应稳定，不依赖数据库自增 ID 作为业务含义。
4. 插入数据前应确保唯一约束能够防止重复语义数据。
5. 字典内容变更后通过新增 migration 调整，不修改历史字典脚本。

## 8. SQL 编写规范

1. 表、字段、索引、约束命名遵守数据库命名规范。
2. 每张表必须明确主键。
3. 业务唯一性必须通过唯一索引或唯一约束体现。
4. 重要字段必须添加 `COMMENT`。
5. 重要业务表默认使用逻辑删除字段 `is_deleted`。
6. 重要业务表保留 `created_at`、`updated_at`。
7. 需要并发修改保护的业务表保留 `version` 字段。
8. 大文本字段优先评估 `TEXT`、`LONGTEXT` 的实际必要性。
9. 金额、分数、经纬度等精确值优先使用 `DECIMAL`，不用浮点数表达精确业务值。
10. 不直接使用 MySQL 关键字作为表名或字段名。
11. 不使用 `SELECT *` 写入视图、初始化校验或迁移辅助语句。
12. 不在 migration 中写环境相关绝对路径。
13. 不在 migration 中创建临时调试对象后遗留到库中。

## 9. 外键与索引规则

1. 核心配置表、关系表可按数据库设计创建物理外键。
2. 日志表、大数据量采集表、图谱三元组表可只保留逻辑外键。
3. 多态关联字段如 `source_type + source_id`、`biz_type + biz_id` 不创建物理外键。
4. 外键是否创建应和数据库设计说明保持一致。
5. 索引不追求一次性过度创建，应围绕唯一性、查询条件、排序分页和关联查询设计。
6. 索引命名使用 `idx_表名_字段名`。
7. 唯一索引命名使用 `uk_表名_字段名`。
8. 外键命名使用 `fk_当前表_关联表`。

## 10. 禁止与慎用操作

禁止在已提交 migration 中执行：

1. 删除历史 migration。
2. 修改已经被团队执行过的 migration。
3. 写入个人账号、密码、Token。
4. 插入测试数据或演示数据。
5. 使用无条件 `DELETE`、`UPDATE`、`TRUNCATE`。
6. 使用和 MySQL 8.0.x 不兼容的数据库方言。

慎用操作：

1. `DROP TABLE`。
2. `DROP COLUMN`。
3. 修改字段类型或长度。
4. 重命名表或字段。
5. 大表新增非空字段。
6. 大表新增多个索引。
7. `flyway repair`。
8. `flyway clean`。

慎用操作必须先说明影响范围，并经小组确认后执行。

## 11. 环境执行规则

| 环境       | 允许操作                                        | 禁止操作                                    |
| ---------- | ----------------------------------------------- | ------------------------------------------- |
| 本地开发库 | `info`、`migrate`、`validate`、必要时重建本地库 | 修改已提交 migration 后继续开发             |
| 共享开发库 | `info`、`migrate`、`validate`                   | `clean`、随意 `repair`、执行未合并脚本      |
| 测试库     | `info`、`migrate`、`validate`                   | `clean`、跳版本执行、手工改表               |
| 生产库     | 经确认后的 `migrate`、`validate`                | `clean`、随意 `repair`、临时 SQL 直接改结构 |

本地开发库需要重建时，优先重建本地数据库或 Docker volume。共享库、测试库、生产库不得使用 `flyway clean`。

根目录命令 `pnpm db:clean:local` 已做基础保护，仅允许连接本地数据库主机，且数据库名必须以 `_dev` 结尾。

## 12. 标准执行流程

新增或执行数据库 migration 前，建议按以下流程操作：

1. 拉取最新代码。
2. 查看 `docs/05_数据库详细设计说明书_V1.0_全组_20260710.md` 和命名规范。
3. 检查最新 migration 版本号。
4. 新增一个版本号更大的 migration 文件。
5. 在本地 MySQL 8.0.x 空库执行迁移。
6. 执行 Flyway 校验。
7. 启动后端确认数据库连接正常。
8. 提交 migration、相关代码和文档。

命令使用说明见 [10_脚本命令使用指南_V1.0_全组_20260707.md](10_脚本命令使用指南_V1.0_全组_20260707.md)。

## 13. 错误处理规则

1. 本地 migration 执行失败时，可以先修复当前未提交脚本后重建本地库再执行。
2. migration 已提交但尚未被其他成员执行时，可以在沟通后修正。
3. migration 已被其他成员或共享环境执行后，不得再修改原脚本，应新增修复脚本。
4. 校验失败时，先检查是否有人修改了历史 migration。
5. `flyway repair` 只用于确认修复元数据问题，不用于掩盖脚本内容不一致。
6. 不通过手工改 `flyway_schema_history` 表来绕过问题。

## 14. 评审检查清单

提交 migration 前至少检查：

1. 文件名是否符合 `VYYYYMMDD_序号__英文描述.sql`。
2. 是否以 MySQL 8.0.x 为准。
3. 是否和数据库设计说明一致。
4. 是否包含不应提交的测试数据或个人数据。
5. 是否有必要的主键、唯一约束、索引和注释。
6. 是否修改了历史 migration。
7. 是否能在空库按顺序执行。
8. 是否已经说明对后端实体、接口或前端页面的影响。

## 15. 已接入命令

当前已经接入独立 `flyway` 模块，并提供以下根目录命令：

| 命令                  | 作用                                |
| --------------------- | ----------------------------------- |
| `pnpm db:info`        | 查看 Flyway 迁移状态                |
| `pnpm db:migrate`     | 执行数据库迁移                      |
| `pnpm db:validate`    | 校验 migration 与数据库历史是否一致 |
| `pnpm db:repair`      | 修复 Flyway 元数据                  |
| `pnpm db:clean:local` | 清空本地开发库对象                  |

其中 `db:clean:local` 只能面向本地开发库，且命令名必须明确包含 `local`，避免误用于共享或生产数据库。
