## 1. 总体结论

当前 M05、M06、M19、M20 四个模块已经具备接入完整项目的基础条件，但还不能理解为“其他模块完成后无需改动即可完全发挥作用”。

更准确的结论是：

1. **M05 文件资源模块可以作为公共文件底座接入完整项目。**
   当前已经具备上传、预览、下载、元数据保存、业务绑定、文件访问日志等能力。其他业务模块完成后，可以通过 `fileId`、`bizType`、`bizId` 与本模块建立关联。

2. **M06 操作审计模块可以作为公共日志底座接入完整项目。**
   当前已经具备操作日志、登录日志、文件访问日志、数据同步日志的基础写入与查询能力。其他模块完成后，可以通过调用 `AuditLogService` 或使用审计注解写入日志。

3. **M19 SOAP 数据交换模块可以接入完整项目，并已预留标准业务导入扩展点。**
   当前可以创建 SOAP 任务、模拟 XML 响应、解析 XML、写交换记录、写同步日志，并通过 `SoapBusinessImportHandler` 预留 M09 生长采集 Service 接入点。由于 M09 目前尚未实现，当前仍不能真正写入生长采集业务表，但已经具备“交换 -> 解析 -> 导入扩展点 -> 交换日志 -> 同步日志 -> 首页失败待办”的基础闭环。

4. **M20 首页看板模块可以接入完整项目，但完整数据范围仍依赖权限体系。**
   当前可以对药材、基地、生长采集、课程、文件、申报审核、业绩认定、SOAP 失败任务等数据做基础聚合；待办已覆盖生长采集审核、申报审核、业绩审核和 SOAP 失败处理；首页汇总会写入当天 `stat_dashboard_snapshot` 快照。角色过滤已做轻量实现，但真正按角色、组织、部门、数据范围过滤仍需 M01-M03 权限模块接入后替换。

因此，四个模块的接入状态可以概括为：

| 模块 | 是否能接入完整项目 | 当前状态 | 主要前置条件 |
|---|---|---|---|
| M05 文件资源 | 可以接入 | 基础功能已具备 | 其他业务模块约定 `bizType`、`bizId`、`fileId` 使用方式，接入权限校验 |
| M06 操作审计 | 可以接入 | 基础功能已具备，同步日志追踪字段已补强 | M01 登录认证完成，其他模块主动调用审计服务或添加审计注解 |
| M19 SOAP 数据交换 | 可以接入，但真实业务入库依赖 M09 | 已具备导入扩展点和日志追踪闭环 | M09 等业务 Service 完成后，实现 `SoapBusinessImportHandler` |
| M20 首页看板 | 可以接入，但完整角色数据范围依赖权限模块 | 已覆盖采集/申报/业绩/SOAP 待办，并写入当天快照 | M01-M03 权限体系、M08、M09、M12、M17、M18 等业务表和状态字段稳定 |

### 3.1 数据库连接与 Flyway 脚本

当前 Flyway 脚本位置：


```text

```

```yaml
spring:
  flyway:
    enabled: ${FLYWAY_ENABLED:false}
    locations: classpath:db/migration
    baseline-on-migrate: true
```

对接完整项目时需要注意：

1. 本地或服务器需要连接 MySQL。
2. 如果希望启动时自动建表，需要设置：

```powershell
$env:FLYWAY_ENABLED="true"
```

3. `V1__m05_m06_m19_m20.sql` 建立四个模块基础表。
4. `V2__m19_data_sync_log_trace_fields.sql` 为 `log_data_sync` 增加 SOAP 任务、交换记录、业务记录和外部编号追踪字段。

7. 如果项目已有完整建表脚本，需要避免重复建表、重复索引或字段冲突。
8. 如果最终数据库由统一 SQL 初始化，本模块脚本可以作为参考，但要和总库表结构保持一致。

### 3.2 M01 身份认证与权限模块

当前 `SecurityConfig` 为开发阶段配置：

```java
.authorizeHttpRequests(auth -> auth.anyRequest().permitAll())
```

这意味着所有接口暂时允许访问，适合开发和单模块测试，但不适合完整项目。

完整项目接入时必须完成：

| 任务 | 说明 |
|---|---|
| 接入 JWT 或 Session 登录 | 登录后能识别当前用户 |
| 替换 `permitAll()` | 文件、审计、SOAP、看板接口需要权限控制 |
| 改造 `CurrentUserUtils` | 从认证上下文中获取真实 userId、username、角色 |
| 文件访问权限 | 只有有权限的人才能预览、下载业务附件 |
| 日志查询权限 | 普通用户不能随意查看全系统日志 |
| 首页数据范围 | 不同角色看到的统计和待办应不同 |

如果 M01 没接入，M05/M06/M20 仍然能跑，但审计日志里的操作者可能是 `anonymous` 或 `0`，无法满足“谁在什么时候做了什么”的完整验收要求。

## 4. M05 文件资源模块对接方案

### 4.1 推荐对接方式

其他业务模块不要直接保存本地文件，也不要重复实现上传逻辑。推荐统一走 M05：

1. 前端调用 `POST /api/files` 上传文件。
2. M05 保存文件到本地存储目录。
3. M05 写入 `sys_file_resource`。
4. 如果请求中带了 `businessType`、`businessId`，同时写入 `sys_file_business`。
5. M05 返回 `fileId`。
6. 业务模块保存自己的业务记录时，保存 `fileId` 或通过 `sys_file_business` 查询附件。

### 4.2 生长采集模块对接

M09 生长采集记录上传图片时建议流程：

```text
新增生长采集记录 -> 得到 recordId
上传采集图片 -> /api/files
绑定业务对象 -> businessType=herb_growth_record, businessId=recordId
必要时 M09 写 herb_image 表保存图片业务字段
```

如果 M09 有 `herb_image` 表，建议这样分工：

| 表 | 作用 |
|---|---|
| `sys_file_resource` | 保存统一文件元数据 |
| `sys_file_business` | 保存文件与采集记录的通用关联 |
| `herb_image` | 保存采集图片的业务属性，例如药材、采集记录、识别状态 |

### 4.3 课程资源模块对接

M12 实验课程资源建议流程：

```text
上传课件或视频 -> /api/files
保存 edu_course_resource -> 写入 courseId、fileId、resourceType、fileUrl 兼容字段
绑定业务对象 -> businessType=edu_course, businessId=courseId
```

### 4.4 评价申报和业绩认定对接

M17、M18 需要上传大量证明材料，建议统一流程：

```text
上传附件 -> /api/files
保存 eval_attachment 或 performance_material -> 写入 fileId
绑定业务对象 -> businessType=eval_application / performance_record
审核时调用 M06 写操作日志
```

### 4.5 M05 仍需补齐的任务

| 优先级 | 任务 | 原因 |
|---|---|---|
| 高 | 接入权限校验 | 防止无权限下载、预览业务附件 |
| 高 | 真实校验业务对象是否存在 | 当前只校验 `bizType` 和 `bizId` 格式 |
| 高 | 明确 `fileUrl` 访问策略 | 当前真实下载接口是 `/api/files/{fileId}/content` |
| 中 | 增加文件类型白名单和更细的大小限制 | 防止上传非法文件 |
| 中 | 删除时同时处理物理文件或标记状态 | 当前删除策略需要和业务保留要求统一 |
| 中 | 支持对象存储扩展 | 后续部署到服务器时更稳定 |

## 5. M06 操作审计模块对接方案

### 5.1 推荐对接方式

其他模块有两种方式接入 M06。

第一种：在业务 Service 中手动调用。

```java
AuditRecordDTO dto = new AuditRecordDTO();
dto.setOperationModule("M09_GROWTH");
dto.setOperationType("AUDIT");
dto.setBizType("herb_growth_record");
dto.setBizId(recordId);
auditLogService.record(dto);
```

第二种：在关键方法上添加审计注解。

```java
@AuditLogAnnotation(
        module = "M09_GROWTH",
        operationType = "CREATE",
        bizType = "herb_growth_record")
public GrowthRecordVO create(GrowthRecordCreateDTO dto) {
    ...
}
```

如果需要记录准确的 `bizId`、审核结果、失败原因，建议优先使用手动调用，因为当前注解还不能自动解析方法参数中的业务 ID。

### 5.2 必须记录日志的业务动作

完整项目中建议以下动作都接入 M06：

| 模块 | 关键动作 |
|---|---|
| M01 身份认证 | 登录成功、登录失败、退出登录 |
| M05 文件资源 | 上传、预览、下载、删除、绑定、解绑 |
| M09 生长采集 | 新增采集、提交审核、审核通过、退回 |
| M12 实验课程 | 新增课程、上传课程资源、删除课程资源 |
| M17 评价申报 | 提交申报、审核、归档 |
| M18 工作业绩 | 填报业绩、上传证明、认定、退回 |
| M19 SOAP 数据交换 | 创建任务、执行交换、解析失败、导入成功、重试 |

### 5.3 M06 仍需补齐的任务

| 优先级 | 任务 | 原因 |
|---|---|---|
| 高 | 接入真实登录用户 | 否则日志无法准确展示操作者 |
| 高 | 替换开发阶段 `permitAll()` | 日志查询属于敏感接口 |
| 中 | 补充接口耗时、请求参数摘要 | 当前已记录请求方法和 URI，耗时和参数摘要仍未记录 |
| 中 | 完善注解能力 | 支持从参数或返回值中解析 `bizId` |
| 中 | 完善数据变更日志 | `log_data_change` 目前只有表和实体，业务写入能力不足 |
| 中 | 日志查询增加时间范围筛选 | 便于答辩和后台管理页面使用 |

## 6. M19 SOAP 数据交换模块对接方案

### 6.1 当前能接入的部分

M19 当前已经可以接入完整项目的“交换记录、同步日志和业务导入扩展点”部分。

当前流程：

```text
创建 SOAP 任务
-> 获取模拟 XML
-> 解析 XML
-> 查找支持当前 resourceType 的 SoapBusinessImportHandler
-> 如果处理器存在，则调用处理器导入业务数据
-> 如果处理器不存在，则返回 PREPARED，表示已解析、待业务模块接入
-> 写 soap_exchange_record
-> 写 log_data_sync
-> 写 log_operation
-> 返回解析结果
```

这个流程可以展示系统具备对接校内 SOAP 系统的基础能力。当前没有 M09 时，流程会停在 `PREPARED`；M09 完成后，只要实现导入处理器，就能把解析结果导入生长采集业务。

### 6.2 完整项目应补齐的闭环

完整项目要求的流程应是：

```text
外部 SOAP 系统推送或系统主动拉取
-> 接口鉴权
-> XML 解析
-> 字段映射
-> 数据校验
-> 调用业务 Service 入库
-> 写 soap_exchange_record
-> 写 log_data_sync
-> 写 log_operation
-> 首页看板统计更新
```

当前不是完全没有“调用业务 Service 入库”的结构，而是已经把这一段抽象成 `SoapBusinessImportHandler`。真正缺少的是 M09 生长采集模块自己的导入处理器实现。

### 6.3 与 M09 生长采集模块对接

M09 完成后，建议 M09 提供一个标准导入接口，例如：

```java
public interface GrowthRecordService {
    GrowthRecordVO importFromSoap(GrowthImportDTO dto);
}
```

然后在 M09 或 SOAP 集成包中实现 `SoapBusinessImportHandler`：

```java
@Component
public class GrowthRecordSoapImportHandler implements SoapBusinessImportHandler {

    private final GrowthRecordService growthRecordService;

    @Override
    public boolean supports(String resourceType) {
        return "GROWTH_RECORD".equalsIgnoreCase(resourceType);
    }

    @Override
    public SoapBusinessImportResult importData(SoapBusinessImportContext context) {
        GrowthImportDTO dto = convert(context.getParsedData());
        GrowthRecordVO record = growthRecordService.importFromSoap(dto);

        SoapBusinessImportResult result = new SoapBusinessImportResult();
        result.setStatus("IMPORTED");
        result.setBusinessType("herb_growth_record");
        result.setBusinessId(record.getId());
        result.setExternalNo(dto.getExternalNo());
        result.setSuccessCount(1);
        result.setFailureCount(0);
        result.setMessage("SOAP 生长采集数据导入成功");
        return result;
    }
}
```

SOAP 模块解析 XML 后，不应直接写 `herb_growth_record` 表，而应通过 `SoapBusinessImportHandler` 调用 M09 的 Service。

原因：

1. M09 Service 负责校验药材是否存在。
2. M09 Service 负责校验基地、采集人、采集时间。
3. M09 Service 负责设置审核状态、来源类型。
4. M09 Service 负责处理重复采集编号。
5. M09 Service 负责维护生长采集模块自己的业务规则。

建议导入对象字段：

| 字段 | 说明 |
|---|---|
| `externalNo` | 外部系统编号，用于幂等去重 |
| `herbName` 或 `herbId` | 药材名称或药材 ID |
| `baseName` 或 `baseId` | 基地名称或基地 ID |
| `collectorName` 或 `collectorId` | 采集人 |
| `collectedAt` | 采集时间 |
| `sourceType` | 固定为 `SOAP` |
| `rawXml` | 原始 XML，可用于追溯 |

### 6.4 当前日志闭环状态

本次补强后，M19 的日志链路已经可以支持后续 M09 标准接入：

| 日志位置 | 当前记录内容 |
|---|---|
| `soap_sync_task` | SOAP 任务编号、资源类型、服务名、方法名、方向、状态、重试次数 |
| `soap_exchange_record` | 请求 XML、响应 XML、解析结果、交换状态、错误信息、调用人、调用时间 |
| `log_data_sync` | 同步类型、来源、目标、任务 ID、交换记录 ID、业务类型、业务 ID、外部编号、成功数、失败数、失败原因 |
| `log_operation` | 创建任务、重试任务、执行成功、执行失败等操作审计，并记录请求方法和 URI |

因此，等 M09 实现后，导入成功时可以形成如下追踪链：

```text
soap_sync_task.id
-> soap_exchange_record.task_id
-> log_data_sync.task_id / exchange_id
-> log_data_sync.business_type = herb_growth_record
-> log_data_sync.business_id = herb_growth_record.id
-> log_data_sync.external_no = SOAP 外部编号
```

### 6.5 M19 仍需补齐的任务

| 优先级 | 任务 | 原因 |
|---|---|---|
| 高 | M09 实现 `SoapBusinessImportHandler` | 当前已提供扩展点，但没有 M09 业务 Service 时不能真实入库 |
| 高 | 在 M09 导入逻辑中使用 `externalNo` 做幂等处理 | 防止重复推送产生重复采集记录 |
| 高 | 导入失败时返回明确失败原因 | 方便写入 `log_data_sync.failure_reason` 和答辩展示 |
| 中 | 字段映射持久化 | 当前映射是写死的 |
| 中 | 支持真实 SOAP 客户端 | 后续如需对接校内系统，需要 WSDL/CXF 配置 |
| 中 | 支持资源类型扩展 | 未来可能导入药材档案、基地、课程等数据 |

## 11. 最终判断

四个模块可以顺利接入完整项目，但前提是完成必要的集成任务。

当前实现最适合的定位是：

1. **M05 是文件公共底座。**
   其他模块只要按 `fileId + businessType + businessId` 对接，就可以统一使用上传、预览、下载和附件管理能力。

2. **M06 是审计公共底座。**
   其他模块只要在关键业务动作中调用审计服务，就可以形成“谁在什么时候对什么做了什么”的追踪能力。

3. **M19 是 SOAP 集成底座。**
   当前已经具备任务、解析、交换记录、同步日志、操作审计和业务导入扩展点。等 M09 完成后，实现 `SoapBusinessImportHandler` 即可进入真实业务入库闭环。

4. **M20 是首页聚合入口。**
   当前已经有聚合查询框架，已覆盖生长采集待办、申报审核待办、业绩认定待办和 SOAP 失败待办，并会写入当天统计快照。等 M01-M03 权限体系稳定后，需要把轻量 `roleType` 过滤替换为真实数据范围过滤。

如果不补齐 M01 权限认证、M02/M03 数据范围、M09 业务导入处理器和 Flyway 统一脚本，四个模块仍然可以单独演示，但不能完全满足完整项目的一切要求。
