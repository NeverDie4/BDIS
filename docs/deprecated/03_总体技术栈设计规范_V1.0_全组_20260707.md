# 生物医药数字信息系统总体技术栈设计规范

## 1. 文档定位

本文档用于明确生物医药数字信息系统的总体技术栈方向，作为后续概要设计、详细设计、开发实施和部署交付的基础约定。

当前阶段仅确定总体技术路线，不对尚未讨论完成的后端鉴权方案、日志方案、构建工具细节作强制规定。

## 2. 总体架构设计

系统采用前后端分离架构。

- 前端负责页面展示、用户交互、数据录入、数据查询和可视化展示。
- 后端负责业务逻辑处理、数据管理、接口服务、权限控制、系统集成和文件管理。
- 前后端通过 RESTful API 进行通信。
- 数据持久化使用 MySQL 8.0.x。
- 缓存服务使用 Redis。
- 后端 ORM 框架使用 MyBatis Plus。
- 版本管理使用 Git。
- 部署阶段采用 Docker 容器化部署。
- 开发阶段不强制要求使用 Docker，可根据团队开发习惯进行本地开发。

## 3. 前端技术栈

| 分类 | 技术选型 |
| --- | --- |
| 前端框架 | React |
| 开发语言 | TypeScript |
| 页面开发 | React 组件化开发 |
| 前后端通信 | RESTful API |
| 数据格式 | JSON |

前端总体要求：

- 前端统一使用 React + TypeScript。
- 页面、组件、接口数据结构应尽量使用 TypeScript 类型定义。
- 前端应按页面、组件、接口、工具方法等进行模块化组织。
- 接口请求建议统一封装，避免在页面中分散编写重复请求逻辑。
- 前端状态管理、路由方案、UI 组件库、构建工具暂不在本文档中强制规定，后续根据项目复杂度和团队习惯确定。

## 4. 后端技术栈

| 分类 | 技术选型 |
| --- | --- |
| 后端框架 | Spring Boot |
| 开发语言 | Java |
| 接口风格 | RESTful API |
| ORM 框架 | MyBatis Plus |
| 数据库 | MySQL 8.0.x |
| 缓存 | Redis |

后端总体要求：

- 后端统一基于 Spring Boot 开发。
- 后端对外提供 RESTful API。
- 数据库访问层使用 MyBatis Plus。
- 业务数据存储在 MySQL 8.0.x 中。
- 高频数据、临时数据、会话类数据或统计类数据可根据实际场景使用 Redis。
- 后端应按 Controller、Service、Mapper、Entity/DTO/VO 等层次组织代码。
- 后端鉴权方案暂未确定，后续可根据系统用户体系、校内系统集成方式和安全要求单独设计。
- 后端日志方案暂未确定，后续应统一日志格式、日志级别、业务审计和异常记录要求。

## 5. 前后端通信规范

前后端通信统一采用 RESTful API。

接口设计原则：

- 使用 HTTP 方法表达业务操作。
- 使用 JSON 作为主要数据交换格式。
- 接口路径应体现业务资源含义。
- 接口返回结构应保持统一。
- 前端不得直接访问数据库，所有业务数据通过后端接口获取。

常见 HTTP 方法约定：

| 方法 | 用途 |
| --- | --- |
| GET | 查询数据 |
| POST | 新增数据 |
| PUT | 更新完整数据 |
| PATCH | 更新部分数据 |
| DELETE | 删除数据 |

接口示例：

```text
GET    /api/herbs
GET    /api/herbs/{id}
POST   /api/herbs
PUT    /api/herbs/{id}
DELETE /api/herbs/{id}
```

## 6. 数据库设计规范

| 分类 | 技术选型 |
| --- | --- |
| 数据库 | MySQL 8.0.x |
| ORM | MyBatis Plus |

数据库总体要求：

- 数据库统一使用 MySQL 8.0.x。
- 表结构设计应结合业务模块进行划分。
- 表名、字段名建议使用小写字母加下划线命名。
- 重要业务表建议包含创建时间、更新时间、创建人、更新人等基础字段。
- 涉及审核、评价、业绩认定、数据采集等关键业务，应保留必要的过程记录。
- 高频查询字段应根据实际查询场景建立索引。
- 删除策略可根据业务重要性选择物理删除或逻辑删除，重要业务数据建议采用逻辑删除。

## 7. 缓存设计规范

缓存统一使用 Redis。

Redis 适用场景：

- 高频查询数据缓存。
- 字典数据、配置数据缓存。
- 临时状态数据缓存。
- 统计结果缓存。
- 后续鉴权方案确定后，可根据需要存储会话、令牌或权限缓存。

Redis 使用要求：

- 缓存 key 应保持统一命名风格。
- 缓存数据应设置合理过期时间。
- 数据更新后应考虑缓存更新或缓存失效策略。
- 不建议将长期核心业务数据仅存放在 Redis 中。

## 8. 版本管理规范

由于团队规模较小，版本管理采用简化 Git 流程，不强制使用复杂的 Git Flow。

建议分支策略：

| 分支 | 用途 |
| --- | --- |
| main | 稳定主分支，用于保存可交付版本 |
| feature/* | 功能开发分支，可按需要创建 |
| fix/* | 问题修复分支，可按需要创建 |

版本管理要求：

- 所有代码统一纳入 Git 管理。
- 主分支应保持相对稳定。
- 小功能可在功能分支完成后合并到主分支。
- 紧急修复可使用 fix 分支，完成后合并回主分支。
- 提交信息应简洁说明本次变更内容。

提交信息示例：

```text
feat: 新增中药材分布地图查询
fix: 修复课程资料上传失败问题
docs: 更新技术栈设计规范
```

## 9. 部署设计

系统部署阶段采用 Docker 容器化部署。

部署总体要求：

- 前端构建产物可通过 nginx 容器提供静态资源服务。
- 后端 Spring Boot 应打包为可独立运行的服务镜像。
- MySQL、Redis、后端服务、前端服务可通过 Docker Compose 进行统一编排。
- 开发环境不强制要求 Docker，开发人员可使用本地环境进行开发和调试。
- 测试环境、生产环境应保持配置隔离。
- 数据库密码、Redis 密码、接口密钥等敏感信息不得写死在代码中。
