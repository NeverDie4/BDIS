# 数据库命名规范设计方案

## 一、文档说明

### 1.1 项目基本信息

| 项目项 | 内容 |
|---|---|
| 项目名称 | 生物医药数字信息系统 |
| 项目类型 | 生物医药信息系统、教学科研资源管理系统、后台管理系统 |
| 主要功能模块 | 用户管理、权限管理、中药材资源管理、生长数据采集、地图分布查询、教学资源管理、科研课题管理、培训素材管理、评价申报管理、业绩认定管理、统计分析、SOAP 数据交换、操作审计 |
| 数据库类型 | MySQL |
| 技术栈 | Spring Boot、Vue、MyBatis、MySQL |
| 是否需要多租户 | 否，当前不做完整多租户，但建议预留机构或部门数据隔离字段 |
| 是否需要权限控制 | 是 |
| 是否需要审计日志 | 是 |

### 1.2 适用范围

本规范适用于生物医药数字信息系统的数据库、数据表、字段、索引、约束、字典、日志、审计字段等命名设计，作为后续数据库设计、后端实体类设计、MyBatis 映射、接口开发、联调测试和项目验收的统一依据。

## 二、总体命名原则

### 2.1 统一性原则

数据库对象命名必须采用统一风格，避免同一类对象出现多套命名方式。

推荐统一使用：

```text
小写英文 + 下划线
```

例如：

```text
sys_user
herb_growth_record
created_at
updated_by
```

不推荐同时混用以下风格：

```text
userName
UserInfo
createTime
created_time
gmt_create
用户表
```

### 2.2 可读性原则

命名应能直接反映业务含义，避免使用含义模糊的名称。

推荐：

```text
herb_species
herb_growth_record
edu_course_resource
log_operation
```

不推荐：

```text
data
info
table1
record
temp
```

### 2.3 业务语义清晰原则

表名和字段名应尽量体现所属模块和业务含义。

例如，中药材生长采集数据表不应命名为 `data`，而应命名为：

```text
herb_growth_record
```

教学课程资源表不应命名为 `resource`，而应命名为：

```text
edu_course_resource
```

### 2.4 避免拼音命名

除特殊专有名词外，不建议使用拼音命名。

不推荐：

```text
yaocai
kecheng
shenhe
yonghu
```

推荐：

```text
herb
course
review
user
```

### 2.5 避免缩写滥用

可以使用行业内常见缩写，但不得使用团队内部难以理解的随意缩写。

允许：

```text
api
url
ip
id
no
```

不推荐：

```text
usr
rsc
mgmt
cfg
dt
```

### 2.6 避免数据库关键字

不得直接使用数据库关键字作为表名或字段名，例如：

```text
user
order
group
key
index
desc
```

其中 `status`、`type`、`level` 可作为字段名使用，但必须结合表名和注释明确语义。

如果表名可能与关键字冲突，应添加业务前缀，例如：

```text
sys_user
biz_order
dict_item
```

### 2.7 避免中英文混用

不允许出现如下命名：

```text
user_姓名
药材_info
course_课程
```

推荐全部使用英文：

```text
real_name
herb_name
course_name
```

### 2.8 控制命名长度

命名应清晰但不宜过长。

MySQL 标识符长度建议控制在 64 个字符以内。

推荐：

```text
herb_growth_record
idx_herb_growth_record_species_id
```

不推荐：

```text
herb_medicine_growth_environment_collection_history_record_table
```

## 三、数据库命名规范

### 3.1 命名格式

数据库名称统一使用：

```text
项目简称_环境名
```

### 3.2 命名规则

数据库名应使用小写英文和下划线，不使用大写字母、中文、空格和特殊符号。

### 3.3 推荐数据库名称

| 环境 | 数据库名 | 说明 |
|---|---|---|
| 开发环境 | `biomed_dev` | 开发人员本地或开发服务器使用 |
| 测试环境 | `biomed_test` | 测试、联调、验收前验证使用 |
| 预生产环境 | `biomed_stage` | 上线前模拟生产环境使用 |
| 生产环境 | `biomed_prod` | 正式运行环境使用 |

### 3.4 不推荐命名

| 不推荐命名 | 问题 |
|---|---|
| `BioMed` | 大小写混用 |
| `biomedDB` | 驼峰命名，不符合统一规范 |
| `生物医药数据库` | 中文命名，不利于迁移和维护 |
| `db1` | 语义不清晰 |
| `test` | 无法区分项目归属 |

## 四、表命名规范

### 4.1 基本规则

表名统一使用：

```text
模块前缀_业务对象
```

命名规则如下：

1. 全部使用小写英文。
2. 单词之间使用下划线分隔。
3. 表名应体现业务含义。
4. 不使用复数形式。
5. 不使用 `tb_`、`t_` 等无实际业务意义的前缀。
6. 多对多关系表使用 `rel_` 前缀。
7. 日志表使用 `log_` 前缀。
8. 字典表使用 `dict_` 前缀。
9. 统计分析类表使用 `stat_` 前缀。

### 4.2 表名前缀规则

| 前缀 | 含义 | 示例 |
|---|---|---|
| `sys_` | 系统基础表 | `sys_user`、`sys_department`、`sys_organization` |
| `auth_` | 权限认证表 | `auth_role`、`auth_permission`、`auth_menu` |
| `rel_` | 关系中间表 | `rel_user_role`、`rel_role_permission` |
| `dict_` | 数据字典表 | `dict_type`、`dict_item`、`dict_region` |
| `herb_` | 中药材资源与生长数据表 | `herb_species`、`herb_growth_record`、`herb_distribution` |
| `edu_` | 教学培训类表 | `edu_course`、`edu_training_material` |
| `research_` | 科研课题类表 | `research_project`、`research_achievement` |
| `eval_` | 评价申报类表 | `eval_application`、`eval_review_record` |
| `perf_` | 工作业绩认定类表 | `perf_record`、`perf_identification` |
| `soap_` | SOAP 数据交换类表 | `soap_exchange_record`、`soap_sync_task` |
| `stat_` | 统计分析类表 | `stat_growth_daily`、`stat_resource_usage` |
| `log_` | 日志审计类表 | `log_login`、`log_operation`、`log_api_request` |

### 4.3 多对多关系表命名

多对多关系表推荐使用：

```text
rel_实体1_实体2
```

示例：

```text
rel_user_role
rel_role_permission
rel_course_resource
rel_project_member
```

如果两个实体关系非常明确，也可以使用实体组合命名：

```text
student_course
teacher_course
```

但在本项目中，为了统一风格，优先使用 `rel_` 前缀。

## 五、字段命名规范

### 5.1 基本规则

字段名统一使用：

```text
小写英文 + 下划线
```

示例：

```text
real_name
phone_number
created_at
updated_by
species_id
```

不推荐：

```text
realName
phoneNumber
CreateTime
Sname
姓名
```

### 5.2 主键字段

所有业务表主键统一命名为：

```text
id
```

推荐类型：

```text
BIGINT
```

说明：

1. 主键不承载业务含义。
2. 主键不使用用户名、学号、工号、药材编号等业务字段。
3. 业务编号通过唯一索引保证唯一性。

### 5.3 外键字段

外键字段命名格式：

```text
关联表名去前缀后的业务对象_id
```

常见示例：

| 关联对象 | 外键字段 |
|---|---|
| `sys_user` | `user_id` |
| `auth_role` | `role_id` |
| `sys_department` | `department_id` |
| `sys_organization` | `organization_id` |
| `herb_species` | `species_id` |
| `edu_course` | `course_id` |
| `research_project` | `project_id` |

### 5.4 常见通用字段

| 字段名 | 含义 | 说明 |
|---|---|---|
| `id` | 主键 | 无业务含义的唯一标识 |
| `created_at` | 创建时间 | 记录数据创建时间 |
| `updated_at` | 更新时间 | 记录数据最后更新时间 |
| `created_by` | 创建人 | 记录创建人用户 ID |
| `updated_by` | 更新人 | 记录最后修改人用户 ID |
| `is_deleted` | 是否逻辑删除 | 0 未删除，1 已删除 |
| `deleted_at` | 删除时间 | 逻辑删除时间 |
| `deleted_by` | 删除人 | 执行删除操作的用户 ID |
| `status` | 状态 | 具体枚举值需在字典或注释中说明 |
| `remark` | 备注 | 补充说明 |
| `sort_order` | 排序号 | 数值越小越靠前 |
| `version` | 乐观锁版本号 | 并发修改控制 |
| `tenant_id` | 租户 ID | 当前项目默认不启用，可预留 |
| `organization_id` | 所属机构 ID | 用于机构级数据隔离 |
| `department_id` | 所属部门 ID | 用于部门级数据隔离 |

### 5.5 布尔字段命名

布尔字段推荐使用 `is_`、`has_`、`can_` 前缀。

示例：

```text
is_deleted
is_enabled
has_attachment
can_download
```

布尔字段建议使用：

```text
TINYINT
```

取值规范：

```text
0 否
1 是
```

## 六、主键、外键和关联字段命名规范

### 6.1 主键命名

所有表主键字段统一命名为：

```text
id
```

推荐定义：

```sql
id BIGINT NOT NULL AUTO_INCREMENT COMMENT '主键ID'
```

主键约束命名：

```text
pk_表名
```

示例：

```text
pk_sys_user
pk_herb_species
pk_herb_growth_record
```

### 6.2 业务编号命名

业务编号不得直接作为主键，应作为普通字段并建立唯一索引。

常见业务编号命名：

| 业务对象 | 编号字段 |
|---|---|
| 用户 | `user_no` |
| 学生 | `student_no` |
| 教师 | `teacher_no` |
| 药材 | `herb_no` |
| 课程 | `course_no` |
| 课题 | `project_no` |
| 申报单 | `application_no` |
| 业绩记录 | `performance_no` |

示例：

```text
user_no
herb_no
course_no
project_no
application_no
```

### 6.3 外键字段命名

外键字段统一使用：

```text
业务对象_id
```

示例：

```text
user_id
role_id
species_id
course_id
project_id
organization_id
```

### 6.4 中间表字段命名

中间表字段使用两端实体的外键字段名。

示例表：

```text
rel_user_role
```

核心字段：

```text
user_id
role_id
created_at
created_by
```

示例表：

```text
rel_project_member
```

核心字段：

```text
project_id
user_id
member_role
joined_at
```

## 七、索引命名规范

### 7.1 索引命名格式

| 索引类型 | 命名格式 | 示例 |
|---|---|---|
| 普通索引 | `idx_表名_字段名` | `idx_sys_user_username` |
| 唯一索引 | `uk_表名_字段名` | `uk_sys_user_user_no` |
| 联合索引 | `idx_表名_字段1_字段2` | `idx_herb_growth_record_species_id_collected_at` |
| 唯一联合索引 | `uk_表名_字段1_字段2` | `uk_rel_user_role_user_id_role_id` |
| 全文索引 | `ft_表名_字段名` | `ft_edu_course_resource_title` |

### 7.2 需要建立索引的字段

以下字段通常需要建立索引：

1. 主键字段。
2. 外键字段。
3. 高频查询字段。
4. 高频排序字段。
5. 状态筛选字段。
6. 时间范围查询字段。
7. 唯一业务编号字段。
8. 登录账号、手机号、邮箱等唯一字段。
9. 地图查询中的区域、经纬度、药材品种字段。
10. 审批流程中的状态、提交时间、审核人字段。

### 7.3 索引示例

```text
idx_sys_user_department_id
idx_sys_user_status
uk_sys_user_username
uk_sys_user_user_no
idx_herb_growth_record_species_id_collected_at
idx_eval_application_status_submitted_at
uk_rel_user_role_user_id_role_id
```

### 7.4 索引设计注意事项

1. 不为低区分度字段单独建立过多索引。
2. 联合索引字段顺序应遵循最左前缀原则。
3. 高频写入表应控制索引数量。
4. 日志表、采集数据表等大数据量表应重点关注时间字段索引。
5. 对统计分析场景，可根据查询频率建立按日期、地区、药材品种的联合索引。

## 八、约束命名规范

### 8.1 约束命名规则

| 约束类型 | 命名格式 | 示例 |
|---|---|---|
| 主键约束 | `pk_表名` | `pk_sys_user` |
| 外键约束 | `fk_当前表_关联表` | `fk_herb_growth_record_herb_species` |
| 唯一约束 | `uk_表名_字段名` | `uk_sys_user_username` |
| 检查约束 | `chk_表名_字段名` | `chk_sys_user_status` |

### 8.2 外键约束说明

在生产环境中，是否使用数据库物理外键应根据项目情况决定。

本项目建议：

1. 核心配置表、关系表可使用物理外键。
2. 高频采集数据表、日志表不强制使用物理外键。
3. 即使不使用物理外键，也必须在字段命名、索引和业务逻辑层保持外键语义一致。

### 8.3 示例

```text
pk_sys_user
fk_rel_user_role_sys_user
fk_rel_user_role_auth_role
uk_sys_user_username
uk_sys_user_user_no
chk_sys_user_status
```

## 九、状态字段和枚举字段命名规范

### 9.1 常见枚举字段

| 字段名 | 使用场景 | 示例 |
|---|---|---|
| `status` | 通用状态 | 用户状态、审批状态、课题状态 |
| `type` | 类型 | 资源类型、文件类型、用户类型 |
| `level` | 等级 | 权限等级、预警等级、评价等级 |
| `source` | 来源 | 数据来源、登录来源、采集来源 |
| `category` | 分类 | 药材分类、资源分类、课程分类 |
| `review_status` | 审核状态 | 评价申报、成果认定 |
| `audit_status` | 审计状态 | 数据变更审计 |
| `sync_status` | 同步状态 | SOAP 数据同步状态 |

### 9.2 状态字段取值规范

状态字段必须在字段注释或数据字典中明确枚举含义。

示例：

```text
status：0 禁用，1 启用
is_deleted：0 未删除，1 已删除
review_status：0 草稿，1 已提交，2 审核通过，3 审核驳回
sync_status：0 待同步，1 同步成功，2 同步失败
```

### 9.3 枚举字段设计要求

1. 不允许只存数字但无注释。
2. 不允许同一个字段在不同表中表达完全不同含义。
3. 复杂枚举值应维护到字典表中。
4. 前端展示值不得硬编码，应尽量从字典接口获取。
5. 后端应使用枚举类或常量类统一管理状态值。

## 十、时间字段命名规范

### 10.1 统一时间字段风格

系统统一使用：

```text
动作过去式_at
```

示例：

```text
created_at
updated_at
deleted_at
submitted_at
approved_at
reviewed_at
started_at
ended_at
collected_at
synced_at
```

### 10.2 常见时间字段

| 字段名 | 含义 |
|---|---|
| `created_at` | 创建时间 |
| `updated_at` | 更新时间 |
| `deleted_at` | 删除时间 |
| `submitted_at` | 提交时间 |
| `approved_at` | 审批通过时间 |
| `reviewed_at` | 审核时间 |
| `started_at` | 开始时间 |
| `ended_at` | 结束时间 |
| `collected_at` | 数据采集时间 |
| `uploaded_at` | 文件上传时间 |
| `downloaded_at` | 文件下载时间 |
| `logged_in_at` | 登录时间 |
| `operation_time` | 操作时间 |
| `synced_at` | 同步时间 |

### 10.3 禁止混用的时间字段风格

不推荐在同一项目中同时出现：

```text
create_time
created_time
gmt_create
insert_time
add_time
ctime
```

本项目统一使用：

```text
created_at
updated_at
```

## 十一、审计字段命名规范

### 11.1 适用场景

本项目涉及用户权限、审批申报、数据采集、资源上传、后台管理和数据交换，因此需要审计字段。

以下表建议包含审计字段：

1. 用户管理表。
2. 权限管理表。
3. 中药材资源表。
4. 生长数据采集表。
5. 教学资源表。
6. 科研课题表。
7. 评价申报表。
8. 工作业绩认定表。
9. SOAP 数据交换表。
10. 后台配置表。

### 11.2 通用审计字段

| 字段名 | 含义 |
|---|---|
| `created_by` | 创建人 |
| `updated_by` | 更新人 |
| `deleted_by` | 删除人 |
| `approved_by` | 审批人 |
| `reviewed_by` | 审核人 |
| `operator_id` | 操作人 ID |
| `operation_time` | 操作时间 |
| `operation_ip` | 操作 IP |
| `operation_result` | 操作结果 |
| `operation_desc` | 操作描述 |

### 11.3 审计字段使用规范

1. `created_by`、`updated_by` 存储用户 ID。
2. 操作日志表中使用 `operator_id` 表示执行操作的用户。
3. 审批场景中使用 `approved_by`、`approved_at`。
4. 审核场景中使用 `reviewed_by`、`reviewed_at`。
5. 系统自动操作可使用固定系统用户 ID，或使用 `operator_type` 区分人工操作和系统操作。

## 十二、日志表命名规范

### 12.1 日志表命名方式

日志类表统一使用：

```text
log_业务动作
```

推荐日志表：

| 表名 | 含义 |
|---|---|
| `log_login` | 登录日志 |
| `log_operation` | 操作日志 |
| `log_api_request` | API 请求日志 |
| `log_data_change` | 数据变更日志 |
| `log_file_access` | 文件访问日志 |
| `log_soap_exchange` | SOAP 数据交换日志 |

### 12.2 日志表字段命名建议

通用日志字段：

| 字段名 | 含义 |
|---|---|
| `id` | 主键 |
| `trace_id` | 请求追踪 ID |
| `operator_id` | 操作人 ID |

### 12.3 日志表设计注意事项

1. 日志表数据量通常较大，应建立时间字段索引。
2. 请求参数和响应内容可能较长，建议使用 `TEXT` 类型。
3. 涉及密码、身份证、手机号等敏感字段时，日志中必须脱敏。
4. 日志表原则上不做物理删除，可按时间归档。
5. 高频日志表可按月分表或定期归档。

## 十七、落地执行要求

1. 数据库建模阶段必须优先遵循本规范。
2. 表结构设计完成后，应统一检查表名、字段名、索引名、约束名是否符合规范。
3. 后端实体类、DTO、VO、Mapper XML 中的字段映射应与数据库命名保持一致。
4. MyBatis 映射时，数据库字段使用下划线命名，Java 属性使用小驼峰命名。
5. 所有核心字段必须添加字段注释。
6. 状态字段、类型字段、来源字段必须在字典表或注释中明确枚举值。
7. 审批、权限、数据采集、后台操作等关键业务必须保留审计字段。
8. 日志表和采集数据表应重点考虑时间字段索引和数据归档策略。
9. 项目组成员新增表或字段前，应先检查是否已有同义字段，避免重复设计。
10. 数据库命名规范应作为代码评审和数据库评审的检查项。

## 十八、总结

本项目数据库命名统一采用小写英文加下划线风格，以模块前缀区分系统基础、权限认证、中药材资源、教学科研、评价申报、业绩认定、数据字典、日志审计和统计分析等业务域。

通过统一数据库名、表名、字段名、主键、外键、索引、约束、状态枚举、时间字段和审计字段命名，可以降低团队协作成本，提高数据库结构的可读性、可维护性和可扩展性，为后续系统开发、接口联调、权限控制、审计追踪和答辩展示提供稳定的数据设计基础。
